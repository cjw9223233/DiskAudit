用 Claude 協作開發：從立規矩到 PR 的完整指南

不論你做的是網站、後端、手機 App、資料分析還是小腳本，這份指南都能直接套用。 內容涵蓋心法、流程、可用的 skill 與指令、Code Review、PR 與 CI、護欄與檢查清單。

怎麼使用這份文件 新手：先讀第 1、2 章，再照第 4 章「一步一步」做一遍。 已經在用：直接查第 5 章 skill 速查、第 9 章提示範本、第 12 章檢查清單。 接新專案：跳到第 3 章「專案啟動清單」，並複製第 8 章的 CLAUDE.md 範本。

1. 核心心法

🧑‍💼 Claude 是資深同事，不是自動駕駛

它能快速讀程式、寫程式、跑測試、寫文件。但「要不要做」與「做對了沒」的責任永遠在你。

🧭 目標清楚，它才走得準

越模糊的需求越需要你驗收。好需求 = 目標 + 範圍 + 驗收方式 + 限制。

🛟 先有安全網再動手

先 commit 乾淨狀態、有測試、有分支。出事時一鍵還原，這是用 AI 協作最便宜的保險。

🔍 信任但要驗證

要求它如實回報「沒驗證到的部分」。「應該可以」不等於「驗證過」。

一個真實的教訓 曾有一次，Claude 把「已經有內容的資料夾」誤當成新資料夾，覆寫了兩個檔案。事後因為來源還在，才得以還原。 如果當時資料夾已在 git 裡、改完看過 git diff，幾秒內就能發現並還原。 所以：先 commit，再讓它改；改完先看 diff，再 commit。

誰負責什麼

事項Claude 可以做一定要你決定
理解程式碼讀檔案、畫資料流、找風險點哪些行為是「刻意的設計」
實作寫程式、補測試、重構、修 bug需求取捨、優先順序
審查找 bug、簡化、查安全問題哪些發現要修、哪些接受風險
版本控制寫 commit 訊息、開 PR、處理衝突push、merge、發版的核准
危險動作先預覽、列出影響刪檔、改正式環境、動憑證的核准

2. 整體流程總覽

  1. 立規矩/init 產生 CLAUDE.md
  2. 想清楚Plan 模式，核准後才動手
  3. 開分支一個需求一條分支
  4. 實作＋測試小步前進、跑測試
  5. 審查review / simplify / security
  6. commit / PR你核准後推送
  7. CI＋合併測試過、人工核准
  8. 維運排程、監控、回顧
經驗法則 小事（改文字、改設定、單檔小 bug）可以直接說；中大型事（新功能、重構、動資料或刪除邏輯）一律先 Plan。

4. Step by Step：做一個功能的標準走法

以「新增一個功能」為例，修 bug、重構的差異見第 4.2 節。

  1. 確認起點是乾淨的

    在專案資料夾執行：

    git status          # 應該沒有未提交的變更
git switch -c feat/你的功能名稱

    有未提交變更就先 commit 或 stash。這一步讓你之後能用 git diff 精準看到 Claude 改了什麼。

  2. 用 Plan 模式描述需求

    切到 Plan 模式（不會改檔），貼上需求。好需求長這樣：

    目標：使用者可以在設定頁匯出 CSV。
範圍：只改 settings 模組與其測試；不改資料庫結構。
驗收：1) 點匯出得到 UTF-8 CSV  2) 空資料時給友善提示  3) 新增的測試全過
限制：不新增第三方套件；沿用現有錯誤處理風格。
請先列出會動到哪些檔案、風險與測試計畫，等我核准再動手。

    審閱它的計畫：範圍是否過大？有沒有漏掉邊界情況？不對就要求修改計畫，核准後才讓它實作。

  3. 讓它小步實作並跑測試

    核准後讓 Claude 實作。要求它：

    • 每完成一小段就跑測試，不要一次改一大坨。
    • 同時補上測試（先寫會失敗的測試，再讓它通過，最可靠）。
    • 結束時回報：改了哪些檔、測試結果、哪些沒驗證到。

  4. 你自己看一遍 diff

    git diff --stat      # 先看改了哪些檔、各多少行
git diff             # 再看細節

    檢查：有沒有動到你沒要求的檔案？有沒有放寬安全規則、刪掉測試、寫死路徑或機密？

  5. 跑審查指令

    依序執行（詳見第 5、6 章）：

    /code-review high      # 找 bug
/simplify              # 收尾：去重複、簡化
/security-review       # 動到權限、刪除、輸入處理、網路時必跑

    對每個發現決定：修 / 不修（寫理由）/ 另開 issue。

  6. commit 與開 PR

    git add -A
git commit -m "feat: 設定頁新增 CSV 匯出"
git push -u origin feat/你的功能名稱

    然後請 Claude 開 PR（或在桌面 app 點「建立 PR」）。PR 說明格式見第 7 章。

  7. 等 CI、人工核准、合併

    CI 全綠、你看過 PR 內容後，由你按 merge。若 CI 失敗，可請 Claude 讀失敗記錄修正（或開啟 Auto-fix），修完再推送。

  8. 收尾與回顧

    刪除已合併的分支；若發現 Claude 反覆犯同樣錯誤，把規則補進 CLAUDE.md，讓下次自動遵守。

4.2 不同工作類型的差異

類型起手式重點
修 bug「先重現問題 → 寫一個會失敗的測試 → 修到測試通過」測試先行；確認修的是根因而不是症狀
重構「不改外部行為。先確認現有測試涵蓋，再小步重構」每步都跑測試；一個 PR 只做重構，不夾帶新功能
接手陌生專案「讀 README 與主要入口，用 5 句話說明資料流，並指出最容易壞的 3 個地方」先只讀不改；產出 /init 的 CLAUDE.md 後再動手
緊急修補 (hotfix)從主分支開 hotfix/*，只改必要的最小範圍仍要測試與 PR；事後補回歸測試與回顧
升級相依套件「一次只升一個；列出 breaking changes；跑完整測試」小 PR；保留可回滾
寫文件「依目前程式碼更新 X 章節，不要改其他段落」限制範圍，避免整份被重寫
資料／腳本類「先預覽（dry-run），不要實際寫入或刪除」寫入前列出影響筆數；破壞性動作需明確核准

5. 可用的 Skill 與指令速查

注意 實際可用的指令依你的版本與安裝的外掛而異。在對話中輸入 / 會列出目前可用者；下表是常見且與一般軟體專案相關的。
指令 / Skill用途什麼時候用
/init分析專案並建立 CLAUDE.md（專案規則與常用指令）新專案第一件事；接手專案時
/code-review審查目前改動、找出正確性問題。可加等級 low medium high xhigh max；--fix 套用修正；--comment 貼成 PR 行內留言；--max-findings <n> 限制數量；可指定 PR 編號、分支或路徑每個 PR 前；平常 high 即可
/code-review ultra雲端多代理深度審查（可指定 PR 編號）。只有你能觸發、會計費，Claude 無法代你啟動；需為 git repo大改動、發版前的最後把關
/simplify找重複、可簡化、效率問題，並直接修（只做品質，不抓 bug）功能完成後收尾
/security-review針對待提交變更做安全審查動到登入、權限、輸入處理、檔案/網路、刪除或金流邏輯時必跑
/run實際啟動並操作專案，確認改動在真實環境有效測試過了還要「親眼看到它會動」時
/schedule建立定期（或一次性）執行的雲端排程任務每週依賴檢查、每月報表、定時巡檢
/loop依間隔重複執行某個提示或指令短期內反覆檢查某狀態
/update-config設定 hooks、權限、環境變數（settings.json）需要「每次都必定發生」的行為（如存檔後自動格式化/檢查）
/fewer-permission-prompts掃描歷史，建議哪些唯讀指令可預先允許嫌權限提示太煩，但不想全放行時
Plan 模式只讀取、規劃，不改檔，等你核准新功能、重構、任何不確定的事
並行 session / worktree同時處理多件互不相干的事，各自獨立工作目錄避免兩件工作互相覆蓋
文件類 skill（docs / docx / pdf / pptx / xlsx）產出可共享文件、Word、PDF、簡報、試算表給主管的報告、規格書、會議簡報
skill-creator把重複的流程做成自己的 skill團隊有固定流程（發版檢查、事故回顧）時
口頭交代 ≠ 保證 「每次改完都要檢查 X」這種規則，用說的只能靠 Claude 記得；要保證每次都發生，請用 hook（/update-config）或 CI。

6. Code Review 怎麼用才有效

6.1 選對等級

等級特性適合
low / medium只回報少數高信心問題小改動、快速自檢
high平衡覆蓋與雜訊一般 PR 的預設選擇
xhigh / max找得最多，但含不確定項、花費較高關鍵模組、重大重構
ultra雲端多代理，最深入，計費發版前、核心安全改動

6.2 發現怎麼處理（Triage）

嚴重度例子處置
阻擋資料遺失、安全漏洞、必現的崩潰、錯誤的計算合併前必修，補回歸測試
重要邊界條件錯誤、錯誤處理缺漏、效能退化本 PR 修，或開 issue 並註明期限
次要命名、重複、風格順手修或忽略；不要讓它拖慢合併
誤報Claude 誤解了設計意圖回覆理由；若常發生，把設計意圖寫進 CLAUDE.md

6.3 審查三件套的順序

  1. /code-review high：先確保「對不對」。
  2. /simplify：再整理「好不好維護」。
  3. /security-review：最後把關「安不安全」。

改完再看一次 git diff，因為審查修正本身也是新的變更。

人類審查者仍然重要 Claude 的審查不能取代團隊成員對「需求是否正確、設計是否合理」的判斷。 建議流程：自己先跑 Claude 審查 → 修完 → 再請同事看 PR，讓同事專注在設計與業務邏輯。

7. PR 與 CI

7.1 前置條件

  • 有遠端 repo（GitHub 等）：git remote add origin <URL> 後 git push -u origin main。沒有遠端就無法開 PR。
  • 安裝並登入 GitHub CLI：gh auth login（PR、issue、CI 查詢都靠它）。
  • 在平台設定分支保護：禁止直接推主分支、要求 PR、要求 CI 通過、（建議）至少一位審查者。

7.2 在 Claude 桌面 app 中

  1. 需求完成後，下一步區塊會出現「建立 PR」按鈕，Claude 會撰寫標題與說明並開 PR。
  2. PR 開出後會綁定該 PR，可開啟 Auto-fix：CI 失敗、合併衝突、審查留言時自動交給 Claude 處理。
  3. Claude 不會自己輪詢 CI，也不會自動 merge（除非你明確要求）。
  4. /code-review --comment 可把審查發現貼成 PR 行內留言。

7.3 好 PR 的標準

項目要求
大小一個 PR 只做一件事；超過約 400 行變更就考慮拆
標題慣例前綴 + 一句話：feat: fix: docs: test: refactor: chore:
說明為什麼改、改了什麼、怎麼測、沒測到什麼、風險與回滾方式
檢查測試全過；動到敏感區域附上 /security-review 結論
回滾說明方法（通常 git revert <commit>）；有資料遷移要寫明

7.4 PR 說明範本

## 為什麼
<問題或需求，一兩句>

## 改了什麼
- <重點 1>
- <重點 2>

## 怎麼測
- [ ] 自動測試：<指令> 全數通過
- [ ] 手動驗證：<步驟與結果>

## 沒測到 / 已知限制
- <誠實列出>

## 風險與回滾
- 風險：<影響範圍>
- 回滾：git revert <commit>（無資料遷移 / 需先執行 ...）

## 審查
- /code-review high：<結論>
- /security-review：<結論或不適用>

7.5 CI 範例（GitHub Actions，請替換測試指令）

# .github/workflows/test.yml
name: test
on:
  pull_request:
  push:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest        # Windows 專案改成 windows-latest
    steps:
      - uses: actions/checkout@v4
      # 依語言設定執行環境，例如：
      # - uses: actions/setup-node@v4
      #   with: { node-version: 20 }
      - name: Run tests
        run: <你的一鍵測試指令>     # 例如 npm test / pytest / dotnet test / ./tests/Run-Tests.ps1

第一次在 CI 上跑，請觀察是否因環境差異（路徑、權限、相依套件）失敗；有 CI 之後，Auto-fix 才有可依據的訊號。

7.6 分支與提交慣例

項目建議
分支名feat/… fix/… docs/… hotfix/…，短命（數天內合併）
commit 大小一個邏輯變更一個 commit；訊息說明「為什麼」
合併方式小團隊常用 squash merge，歷史乾淨；依團隊慣例
版本標記git tag v1.2.0 && git push --tags，遵循語意化版本（主.次.修）

8. CLAUDE.md：讓規則永久生效

CLAUDE.md 是放在專案根目錄、每次對話都會自動讀取的說明檔。把「你不想每次重複交代的事」寫進去：

寫什麼

如何建置／測試／執行、程式風格、禁止事項、重要設計決策與原因、容易踩的坑。

不要寫什麼

顯而易見的事、過長的流水帳、會過期的細節（改放 README 或程式註解）、機密。

怎麼維護

Claude 反覆犯同一個錯 → 補一條規則。規則變了 → 更新它。像程式碼一樣走 PR。

8.1 通用範本（複製後依專案修改）

# <專案名稱> — 給 Claude 的專案規則

## 這個專案是什麼
<一兩句話：用途、主要使用者、技術棧>

## 常用指令
- 安裝相依：<指令>
- 執行：<指令>
- 全部測試：<指令>            # 改完程式一定要跑
- 靜態檢查／格式化：<指令>

## 程式風格
- <語言版本與限制，例如：Python 3.11、不使用 X 語法>
- <命名、目錄結構慣例>
- 檔案編碼／換行：<例如 UTF-8、LF；PowerShell 腳本需 UTF-8 with BOM>

## 不可違反的規則（硬性）
- 不得提交機密（金鑰、密碼、token）。
- 不得刪除或弱化既有測試來讓它通過。
- <專案特有，例如：稽核腳本必須唯讀；資料庫遷移必須可回滾>
- 破壞性操作（刪檔、drop、force push）必須先停下來問我。

## 工作方式
- 新功能與重構：先用 Plan 模式提出計畫，等我核准。
- 改完先跑測試，結束時回報：改了什麼、測試結果、沒驗證到的部分。
- 一個 PR 只做一件事；commit 訊息用 feat:/fix:/docs:/test:/refactor:/chore: 前綴。

## 架構重點
- <主要模組與職責，一行一個>
- <資料流或關鍵設計決策與原因>

## 已知地雷
- <容易出錯的地方、過去踩過的坑>

8.2 Hook：需要「必定發生」時

CLAUDE.md 是「請求」，hook 是「強制」。例如：

  • 每次寫入檔案後自動執行格式化或編碼檢查。
  • 每次 Claude 嘗試執行含 rm -rf、git push --force 的指令時攔截。
  • 每次結束對話前自動跑測試。

設定方式：用 /update-config 描述你要的行為，由 Claude 協助寫入 settings.json，並請它先說明會改哪裡。

9. 提示範本與好需求公式

好需求公式 目標（要達成什麼）＋ 範圍（改哪些、不改哪些）＋ 驗收（怎樣算完成）＋ 限制（不能怎樣做）＋ 回報（要求它說明未驗證處）。
情境範本（點「複製」使用）
新功能
用 Plan 模式：新增 <功能>。
先列出會動到的檔案、風險、測試計畫，等我核准再動手。
修 bug
先重現這個問題：<描述/錯誤訊息>。
寫一個會失敗的測試，再修到通過，並跑全部測試。
說明根因，而不只是症狀。
重構
不改外部行為，重構 <模組>。
先確認現有測試涵蓋；小步進行，每步跑測試；不要夾帶新功能。
動敏感邏輯
這次只改 <預覽/輸出/文字>，不得動 <刪除/寫入/權限> 的路徑。
改完執行 /security-review，並列出任何放寬限制的地方。
提交前自檢
看 git diff，逐檔說明變更。
列出：沒驗證到的地方、做了哪些假設、有沒有動到我沒要求的檔案。
接手專案
先只讀不改。讀 README 與主要入口，
用 5 句話說明資料流，指出最容易壞的 3 個地方，並建議 CLAUDE.md 該寫什麼。
不確定時
先別動手。告訴我你打算改哪些檔、為什麼、有哪些替代方案與取捨。
寫／改文件
依目前程式碼更新 <章節>，只改這一段，其他不要動。
不確定的地方標註「待確認」，不要猜。
CI 失敗
讀這次 CI 失敗的記錄，找出根因並修正。
不要用跳過測試或放寬斷言的方式讓它通過。
事故回顧
根據這次事故整理：時間線、根因、影響、已做與待做的改善，
並建議要補哪些測試與 CLAUDE.md 規則。

10. 護欄與風險管理

🔐 機密

金鑰、密碼、客戶資料不貼進對話、不進 commit。已洩漏就視為外洩並輪換。

🧯 破壞性動作

刪檔、drop table、force push、改正式環境：先預覽，再由你逐項核准。

🔎 驗證

命令與路徑先看過再執行，尤其帶 --force、-Execute、--yes 的。

🪪 權限

預設每次詢問。只對確定安全的唯讀指令放寬；自動核准模式只用在隔離或可丟棄的環境。

💰 成本

ultra、max 等深度審查較貴，大改動才用，平常 high。

📜 責任

Claude 是工具，commit 是你的名字。核准前讀過 diff。

10.1 分級核准建議

動作類型例子建議
唯讀讀檔、搜尋、git status/diff/log、跑測試可預先允許
本機可還原改檔、本機 commit、建分支在 git 保護下可放寬；看 diff
外部／不可逆push、merge、發版、刪資料、改雲端資源、寄信每次都要你核准

10.2 常見反模式

反模式後果改成
沒 commit 就叫它大改看不出改了什麼、難以還原先 commit，開分支

13. 常見問題

Claude 改壞了怎麼辦？

git diff 檢視；git restore <檔案> 還原單檔；git revert <commit> 還原已提交的變更。這就是要先 commit 的原因。

可以直接說「全部幫我處理好」嗎？

小事可以；大事先 Plan。越模糊的需求，越需要你驗收與拆小。

審查抓到很多項目，都要修嗎？

不必。依嚴重度排序，高信心的正確性與安全問題先修，其餘記錄成 issue 或接受風險並寫理由。

它說「測試通過」我就能放心嗎？

要看測試涵蓋什麼。請它列出「測試未涵蓋」的清單，並對這些部分手動驗證。

能讓它自動 merge 嗎？

不建議。預設不會，需你明確要求；合併是發版前最後一道人工關卡。

多人團隊怎麼讓大家遵守同樣規則？

把規則寫進 CLAUDE.md 並 commit；必須每次發生的檢查用 hook 與 CI；分支保護要求 PR 與 CI 通過。

同時做兩件事會互相影響嗎？

會，如果在同一個工作目錄。請用不同分支，或並行 session／worktree，讓各自有獨立目錄。

怎麼讓 Claude 越用越懂我的專案？

把反覆糾正的事寫進 CLAUDE.md；把重複的流程做成自己的 skill；保持 README 與 docs 更新。
